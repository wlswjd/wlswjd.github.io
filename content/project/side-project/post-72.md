유튜브를 보다 보면 이런 순간이 자주 온다.

> “그 ○○이랑 △△ 먹던 편 뭐였지?”

제목/설명에 정답이 있을 때도 많지만, 기억은 늘 단서 몇 개만 남는다.  
그래서 특정 채널(뜬뜬·쑥쑥·채널십오야)의 영상을 수집하고, **RAG(검색 + LLM)** 로 자연어 질문에 답해주는 Streamlit 봇을 만들었다.

---

### 1. 전체 구조 (RAG 파이프라인)

흐름은 단순하지만, “검색 신뢰도”를 높이는 데 포인트가 몰려 있었다.

- (1) 질문 임베딩: 한국어 임베딩 모델(`jhgan/ko-sroberta-multitask`)
- (2) ChromaDB 의미 검색: 메타 청크 + 자막 청크를 함께 검색
- (3) 후보 집계: 청크 단위가 아니라 **`video_id` 단위로 점수 집계**
- (4) 답변 생성: Gemini가 **[제목](링크)** 형태로 추천하도록 포맷 강제
- (5) 실패 대비: LLM 키가 없거나 검색이 약하면 룰 기반 fallback

---

### 2. 데이터 파이프라인: “자막만”으로는 잘 안 맞는다

처음에는 자막만 긁어서 검색했는데, 실전 질문에서 제일 많이 틀린 케이스가 있었다.

- 출연자 이름이 자막에 **음차/별칭**으로만 등장 (예: “최예나” → “예나”)
- 자막이 아예 없거나 차단/실패로 빈 값

그래서 “검색 신호가 강한” 메타데이터를 적극적으로 쓰는 쪽으로 바꿨다.

- **메타 청크(제목+설명+태그)**: 영상 1개당 1개  
  - 검색 신뢰도가 가장 높아서, 이쪽에 **가중치 부스트**를 준다.
- **자막 청크**: 1200자 슬라이딩, 200자 overlap  
  - “대사가 단서”인 질문에 강하다.

수집/처리는 이런 단계로 흘러간다.

~~~text
data_collector.py        -> data/raw/<channel>_raw_data.json
enrich_metadata.py       -> 기존 raw에 description/tags 보강
transcript_rescrape.py   -> 빈 자막만 yt-dlp로 재수집
chunk_data.py            -> 메타 청크 + 자막 청크 생성
build_vector_db.py       -> ChromaDB(persistent) 인덱싱
app.py (Streamlit)       -> 검색/집계 -> Gemini 답변
~~~

---

### 3. 검색 품질을 올린 핵심: video_id 집계 + 메타 청크 가중치

Vector DB 검색은 기본적으로 “청크”를 반환한다.  
그런데 사용자는 “영상”을 원한다. 그래서 결과를 영상 단위로 다시 정리했다.

- 같은 영상에서 여러 청크가 뜨면 **집계 점수 상승**
- 메타 청크는 신뢰도가 높아서 **추가 가중치(+0.15)** 적용

이렇게 바꾸고 나서, “정확히 일치하는 영상은 없지만…” 같은 회피 답변이 눈에 띄게 줄었다.

---

### 4. 성능 이슈: 검색이 느린 이유는 ‘모델 로딩’이었다

의외로 병목은 ChromaDB가 아니라 임베딩 모델이었다.

- 검색마다 `SentenceTransformer`를 새로 만들면 매번 3~5초 로딩

해결은 캐시였다.

- 임베더를 모듈 레벨 싱글턴으로 유지(`vector_store.get_embedder()`)
- Streamlit에서도 `@st.cache_resource`로 1회만 로드
- Chroma query는 1회로 넉넉히 가져온 뒤 video 단위 집계

---

### 5. 운영 이슈: Gemini 답변이 링크 한복판에서 끊기는 문제

한 번은 답변이 이런 형태로 잘렸다.

> “찾으시는 영상은 **[[EN] ...](https://www.youtube.com/watch?v=7j_Oc”

원인은 모델이 reasoning(thinking) 계열일 때, **출력 토큰 예산**을 thinking이 같이 잡아먹는 문제였다.

대응은 3단으로 했다.

- thinking 비활성화 시도(지원 안 되면 자동 fallback)
- `max_output_tokens` 상향(예: 600 → 2000)
- `finish_reason == MAX_TOKENS` + 응답이 비정상(빈 값/너무 짧음)이면 재시도 or 룰 기반 fallback

“잘 되는 경우”만 보는 게 아니라, “망가질 때 복구”까지 넣어둔 셈이다.

---

### 6. UX: 후보 카드가 답변을 방해하지 않게

상위 1개는 본문에서 이미 추천하므로, 카드 리스트에서 중복 노출되면 화면이 산만해진다.

- 1번 후보는 카드에서 제외
- 나머지는 “다른 후보 영상 N개 보기” expander에 접어서 넣기

사용자 시선을 “답변”에 모으는 쪽이 더 좋았다.

---

### 7. 다음 로드맵 (가치 대비 우선순위)

지금 구조에서 검색 품질을 더 끌어올리려면, 다음이 가장 효율적이다.

- **댓글(top comments) 수집**: “그거 ○○ 나온 편” 같은 단서가 댓글에 많다
- **출연자 자동 추출**: description의 해시태그/정규식으로 guests 필드 구성
- **Hybrid retrieval(BM25 + 벡터)**: 고유명사 정확 매칭 보완
- **타임스탬프 기반 청크**: “27분 13초 장면” 같은 답변으로 확장

---

### 마무리

이 프로젝트는 “유튜브 검색”을 대신하려는 게 아니라, **내가 기억하는 단서(자연어)로 회차를 복구**해주는 도구에 가깝다.  
RAG는 결국 **데이터 품질 + 검색 집계 + 실패 복구**의 합이라는 걸 다시 한 번 배웠다.
