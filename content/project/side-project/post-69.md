마인크래프트는 정보가 방대하고 업데이트도 잦다. 그래서 “검색+생성”을 결합한 **RAG(Retrieval-Augmented Generation)**로,
마인크래프트 위키 기반의 정확한 게임 정보 챗봇을 만드는 사이드 프로젝트를 시작했다. 이 글은 시리즈 1편으로 **기반 구축과 데이터 수집**을 정리한다.

---

### 1. 프로젝트 개요

- **목표**: 마인크래프트 위키 데이터를 근거로, 조합법/몹/구조물/명령어 등 질문에 정확히 답하는 RAG 챗봇
- **스택**: Python, LangChain, ChromaDB, Google Gemini API, Streamlit, HuggingFace Embeddings(`jhgan/ko-sroberta-multitask`)

---

### 2. 초기 트러블슈팅: venv를 켰는데 왜 모듈이 없지?

`langchain_community` 같은 패키지를 설치했는데도 `ModuleNotFoundError`가 떠서 한참 헤맸다.

원인은 의외로 `.zshrc`의 alias였다.

- `python`이 시스템 파이썬으로 강제 연결되어, venv가 무시되고 있었다
- alias를 제거하고 `./venv/bin/python`으로 명시 실행하면서 환경 분리를 확실히 했다

이 단계에서 느낀 건, “코드보다 환경이 먼저다”였다.

---

### 3. LLM 연동: 404 NOT_FOUND와 모델 탐색

Gemini를 붙이는 과정에서 `404 NOT_FOUND`가 발생했다. (`gemini-pro`, `gemini-1.5-flash` 등이 인식되지 않음)

그래서 패키지 버전만 의심하지 않고, 아예 API 키 기준으로 “내가 접근 가능한 모델이 뭔지”부터 확인했다.

- `google.generativeai.list_models()`로 모델 목록을 직접 조회
- 해당 키 환경에서는 **`gemini-2.5-flash`**가 활성화되어 있었고, 그에 맞춰 코드를 수정해 연동을 마쳤다

---

### 4. 데이터 “질” 고도화: 3x3 조합법 파서 직접 구현

초기에는 텍스트만 긁어왔는데, 마인크래프트의 핵심인 **제작대 3x3 조합법**을 설명하지 못했다.

그래서 “양을 늘리기 전에 질을 올리자”로 방향을 바꿨다.

- HTML 구조(`mcui-Crafting_Table`)를 분석
- `BeautifulSoup`로 조합 UI를 파싱
- 아이콘 속성(title)을 추출해  
  `[1번칸: 참나무 판자]` 처럼 **좌표 기반 텍스트 데이터**로 변환

이게 되어야, 챗봇이 “조합법” 질문에 제대로 근거를 들고 답할 수 있다.

---

### 5. 데이터 “양” 확장: 공식 위키 자동 수집

공식 위키 API(`action=query`) 기반으로 대량 수집 스크립트를 만들었다.

- **Resume 로직**: `processed_items.txt`로 중복 수집 방지
- **재귀 탐색**: 하위 카테고리까지 내려가며 수집

수집 범위는 아이템/몹/바이옴/구조물/마법/레드스톤/명령어/패치노트 등 핵심을 포함했고, 약 **886개** 문서를 확보했다.

---

### 6. 커뮤니티 팁 보완: 나무위키 크롤링 + 환각 방어

공식 위키만으로는 “실전 팁/글리치/스피드런 테크”가 부족했다.

- 나무위키 팁 문서들을 depth=1로 수집
- 데이터에 `{"source": "namuwiki"}` 메타데이터를 붙여 출처를 분리
- 답변 시 공식 위키 기반이 아닌 경우 **경고 문구를 강제**해 환각 리스크를 낮췄다

추가로 약 **2,231개** 커뮤니티 청크를 확보했다.

---

### 7. 다음 문제: 대화 문맥을 못 잇는다

마지막으로 남은 큰 문제는 “대화 기억”이었다.

예를 들어 “워든” 대화 중에 “잡는 방법이 뭐야?”라고 묻으면, 주어를 잊고 엉뚱한 검색 결과를 가져오는 문제가 있었다.

이건 2편에서 **History-Aware Retriever**로 해결해본다.
