이번 글은 시리즈 3편. “만들었다”에서 끝내지 않고, **평가 기준을 세우고**, **배포 전략을 정하고**, **UI/UX를 서비스 수준으로 다듬는** 단계까지 정리한다.

---

### 1. RAG 성능 평가 기준: The RAG Triad

RAG는 “답을 잘한다”를 하나의 점수로 뭉개면 개선 포인트가 보이지 않는다. 그래서 아래 3개 축으로 나눠서 본다.

- **Context Relevance (문맥 적합성)**: Vector DB가 *질문과 관련 있는* 청크를 제대로 가져왔나?
- **Faithfulness / Groundedness (사실 부합성)**: 답변이 *검색된 컨텍스트에만* 근거하고 있나? (환각 방지)
- **Answer Relevance (답변 관련성)**: 최종 답변이 사용자의 *원래 의도*에 정확히 답하고 있나?

이 3개를 분리해보면, “검색이 문제인지/생성이 문제인지/질문 이해가 문제인지”가 바로 드러난다.

---

### 2. RAG 평가 방법론 정리

실제로 적용(또는 적용 예정)인 평가 방법은 다음과 같다.

- **출처 표기(Citation)**: 어떤 문서를 근거로 답했는지 명시해서 검증 가능성을 확보
- **네거티브 테스트(Negative Testing)**: DB에 없는 질문을 던져서 “모른다/근거가 없다”가 제대로 나오는지 확인
- **LLM-as-a-Judge**: RAGAS, TruLens 같은 프레임워크로 Triad 지표를 자동 채점하는 흐름 학습

“잘 되는 데모”를 넘어 “망가져도 어디가 망가졌는지 알 수 있는 시스템”이 목표다.

---

### 3. 포트폴리오 배포 전략: Streamlit Community Cloud 선택

초기에는 Vercel 블로그 연동도 고민했지만, **Python/Streamlit + 로컬 벡터 DB**를 자연스럽게 운영하기엔 제약이 컸다.

그래서 결론은 **Streamlit Community Cloud**.

- **배포 준비**: `requirements.txt` 구성
- **연동**: GitHub repo 연결
- **보안**: Gemini API Key는 Secrets(환경 변수)로 관리

“누가 봐도 클릭 한 번으로 실행되는 데모”를 만들기 위해 배포 경험까지 포함시키기로 했다.

---

### 4. UI/UX 고도화: 앱이 ‘서비스처럼’ 보이게

기능은 같아도 UX가 안 받쳐주면 신뢰가 떨어진다. 그래서 다음을 손봤다.

- **브랜딩**: 텍스트 이모지 대신 마인크래프트 로고 이미지로 교체
- **레이아웃**: 로고/타이틀을 `st.columns`로 정렬해 밀도 개선
- **사이드바**: 대화 초기화 버튼 + 데이터 소스/모델 정보 패널 추가
- **채팅 UI 모던화**: 커스텀 CSS로 “사용자/AI 메시지”를 시각적으로 분리

결과적으로 “작동하는 코드”에서 “써보고 싶은 앱”에 가까워졌다.
