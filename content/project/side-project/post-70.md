시리즈 2편은 **대화 문맥(Context)**을 붙여서 “챗봇답게” 만드는 과정이다. 만들고 나니 바로 드러난 문제는, 챗봇이 *방금 전 얘기한 주어를 잊어버린다*는 점이었다.

---

### 1. Context Amnesia: 주어를 잃어버리는 문제

문제 상황은 전형적이다.

- 사용자가 “**워든**”에 대해 질문한다
- 다음 질문으로 “**잡는 방법이 뭐야?**”라고 묻는다
- 챗봇은 “워든”을 잊고, DB에서 “잡는 방법”과 관련된 엉뚱한 문서를 가져온다

RAG에서 검색 단계가 흔들리면, 생성이 아무리 좋아도 답이 틀어진다.

---

### 2. 해결: 기록 인지 검색기(History-Aware Retriever) 도입

핵심 아이디어는 단순하다.

> “현재 질문”을 바로 검색하지 말고, **이전 대화 기록을 참고해서 독립형 질문으로 재구성**한 뒤 검색하자.

이를 위해 `create_history_aware_retriever` 기반의 **Query Rewriting** 흐름을 적용했다.

- 입력: `chat_history` + 현재 질문
- 출력: “주어가 포함된” 독립형 질문
- 그 질문으로 Vector DB 검색 → 답변 생성

이렇게 하면 “그래서 체력은 몇이야?” 같은 대명사/생략형 질문도 훨씬 안정적으로 처리된다.

---

### 3. 429 Rate Limit: 좋아졌는데, 호출이 2번이라 비용/제한이 터짐

문제는 최적화였다. Query Rewriting + Answer Generation으로 LLM 호출이 **1 질문당 2회**가 되면서,
Gemini 무료 티어의 RPM 제한에 빨리 걸려 `429 RESOURCE_EXHAUSTED`가 발생했다.

중간에 “이전 질문+현재 질문을 합쳐서 한 번만 호출” 같은 편법도 시도했는데,
**주제가 전환될 때(워든 → 어부 주민)** 검색 품질이 크게 무너지는 문제가 있었다.

---

### 4. 최종 구조: 검색은 현재 질문, 답변은 전체 기록을 읽고 생성

결론은 아래처럼 역할을 분리하는 것이었다.

- **Retrieval(검색)**: 오직 **현재 질문**만으로 수행 (주제 전환 내성 확보)
- **Generation(답변)**: LLM이 **전체 `chat_history`**를 읽고 문맥을 스스로 반영

이렇게 하면 호출은 **1회**로 유지하면서도, 문맥 유지와 주제 전환을 동시에 챙길 수 있다.

---

### 5. 체감 속도 개선: 스트리밍 출력

답변이 “한 번에 툭” 나오면 기다림이 길게 느껴진다. 그래서 스트리밍으로 바꿨다.

- `streaming=True`
- `invoke()` 대신 `stream()` 사용
- Streamlit의 `st.empty().markdown()`으로 chunk를 즉시 렌더링

결과는 단순하지만 강력했다. 사용자는 “멈춘 듯한 화면”을 보지 않아도 된다.
