마인크래프트 위키 데이터를 활용한 지능형 가이드 챗봇 개발을 위한 **단계별 파이프라인과 검색 전략**을 정리함. **2026년 5월 중순** 마감과 **1인 개발**을 전제로, 당장 돌아가게 만들 수 있는 기술 스택과 라이브러리 위주로 구성했음.

---

### 1. 계층적 정보 검색을 위한 데이터 구조화 및 검색 전략

단순 텍스트 청킹(Chunking)만 쓰면 “A를 만들기 위해 B와 C가 필요하다”는 **조합법의 계층적 논리**가 끊길 위험이 큼. 그래서 아래 전략을 기본으로 깔고 감.

*   **구조화된 데이터(JSON) 유지:** 크롤링 결과를 줄글만 쌓아 두지 않고, 아이템 단위로 필드가 고정된 형태로 저장함. 예시는 아래와 같은 느낌.

```json
{
  "item": "곡괭이",
  "recipe": ["나무 막대기 2개", "철괴 3개"],
  "biome": "없음"
}
```

*   **Multi-Vector Retrieval (Parent–Child Document Retriever):** 하나의 아이템 문서를 **여러 하위 벡터**(요약, 특정 재료명, 조합법 문단 등)로 나누어 임베딩함. 사용자가 “철괴가 들어가는 조합법”처럼 **좁은 질의**를 하면 **Child**가 먼저 걸리고, LLM에는 그 Child가 속한 **전체 Parent 문서**(조합 체인·획득처까지 포함)를 넘겨 **정보 누락**을 줄임.

*   **Metadata Filtering (Self-Querying):** 아이템명, 카테고리(무기·건축 블록 등), 바이옴·구조물 태그 등을 벡터 DB **메타데이터**로 두고, 질문에서 조건을 뽑아 검색 전후에 필터링(Self-Querying)해 정확도를 올림.

### 2. 단계별 개발 파이프라인 및 필수 기술 키워드

#### Phase 1: 데이터 수집 및 전처리 (Data Ingestion)

위키 HTML 구조를 보고 필요한 필드만 뽑아 구조화함.

*   **세부 작업:** 아이템·몹·생물군계 등 **대상 페이지 크롤링**; 표(Table)로 된 조합법은 DOM 파싱 후 **JSON**으로 정규화.
*   **키워드:** Web Scraping, DOM Parsing, Data Structuring (JSON)
*   **라이브러리:** **BeautifulSoup4**, (규모 커지면) **Scrapy**, 표 정리·검증용 **pandas**

#### Phase 2: 청킹 및 임베딩 (Chunking & Embedding)

구조화 데이터를 검색·생성 파이프라인이 소화할 수 있는 단위로 나눔.

*   **세부 작업:** 위 1절의 **Parent–Child** 전략에 맞춰 문서 분할; 텍스트는 **임베딩 API** 또는 오픈소스 모델로 벡터화 (비용·한국어 품질·로컬 GPU 유무로 선택).
*   **키워드:** Semantic Chunking, Multi-Vector Retrieval, Text Embedding
*   **라이브러리:** **LangChain** (ParentDocumentRetriever, RecursiveCharacterTextSplitter 등), **OpenAI** `text-embedding-3-small` 또는 **Hugging Face** 계열 임베딩

#### Phase 3: 벡터 DB 구축 (Vector Database)

벡터와 메타데이터를 같이 넣고 **유사도 검색**이 되게 함. 단기·1인이면 **로컬 파일**로 관리되는 쪽이 부담이 적음.

*   **세부 작업:** 임베딩·메타데이터 적재, 인덱스 구성, 필요 시 청크 크기·검색 개수(k) 튜닝.
*   **키워드:** Vector Store, Metadata Indexing, Similarity Search (Cosine 등)
*   **라이브러리:** **ChromaDB** (로컬 운용이 단순한 편), **FAISS** (가벼운 인메모리/파일 옵션)

#### Phase 4: 검색 및 프롬프트 엔지니어링 (Retrieval & Generation)

질의 → 검색 → LLM 순으로 묶는 **RAG** 본체.

*   **세부 작업:** 질문이 “재료 역추적”인지 “획득 장소”인지 등 **의도에 따라 검색 파라미터나 라우팅**을 달리할 수 있게 설계(초기에는 규칙 + 소형 분류도 가능). 검색된 구조화 문서는 LLM이 읽기 좋은 **한 덩어리 프롬프트**로 직렬화. 시스템 프롬프트로 **“제공된 컨텍스트 안에서만, 단계에 맞게 설명”**을 강하게 걸어 환각을 억제.
*   **키워드:** Self-Querying Retriever, Prompt Engineering, RAG Pipeline
*   **라이브러리:** **LangChain** 또는 **LlamaIndex** (구조화·계층 데이터 RAG에 문서화가 잘 된 편)

#### Phase 5: 웹 프론트엔드 연동 및 배포 (Frontend)

데모를 **눈으로 확인**할 수 있게 최소 UI를 올림.

*   **세부 작업:** 채팅 UI, 로딩 표시, 답변은 **마크다운**(표·리스트) 렌더링.
*   **키워드:** Web Application Framework, State Management
*   **라이브러리:** **Streamlit** — Python만으로 프로토타입을 빠르게 뽑기 좋음 (이후 필요하면 FastAPI + React 등으로 이관)

### 3. 데이터 소스 기준: 위키 언어·게임 버전은?

질문으로 남아 있던 부분을 여기서 명시해 둠.

**아직 “문서 한 장” 수준으로 완전히 고정된 상태는 아님.** 대신 **Phase 1 착수 전**에 아래 중 하나로 못 박을 예정임.

| 결정 항목 | 후보와 트레이드오프 |
| :--- | :--- |
| **언어** | **영어 위키**(보통 본문·표가 가장 잘 정비됨, 레시피/ID 이슈가 문서화돼 있음) vs **한국어 위키**(UX·데모 시연은 유리, 표/누락 페이지는 영어 대비 손이 더 갈 수 있음). 1인·기한을 보면 **영어 소스 + 답변만 한국어**가 리스크가 작은 편임. |
| **에디션/버전** | **Java Edition** 위키를 기본으로 두고, 데이터에 `version` 또는 `applies_since` 같은 필드를 두어 **스냅샷/패치**로 갈리는 항목은 메타데이터로 분리하는 쪽을 우선 고려함. Bedrock은 별도 스코프로 두면 범위 폭발을 막기 쉬움. |

정리하면, **소스 위키(언어·네임스페이스)·대상 에디션·재현에 쓸 “기준 버전”** 세 가지를 스프레드시트 한 줄로 적어 두고 크롤러의 시작 URL과 메타 스키마를 그에 맞추면 됨.

---

### 4. 마무리

이 글은 구현 완료 보고가 아니라 **검색이 깨지지 않게 만드는 쪽**에 무게를 둔 설계 메모임. 다음 글부터는 실제로 **어떤 페이지에서 어떤 셀렉터로 표를 뽑았는지**, **Parent/Child를 몇 종류로 쪼갰는지**처럼 재현 가능한 단위로 풀어 쓸 계획임.
