## 1. 왜 평가가 필요한가

RAG 학습 과정에서 Day 1~6에 걸쳐 임베딩, Vector DB, 청킹, Hybrid Search, Re-ranking, 메타데이터 필터링을 배웠습니다. 학습한 내용을 두 개의 사이드 프로젝트(마크 RAG, YT RAG)에 단계적으로 적용했습니다.

문제는 그다음이었습니다.

> "Hybrid Search 도입했더니 진짜 좋아졌나?"

답할 수 없었습니다. 같은 질문을 던지면 적용 전과 후 모두 그럴듯한 답변이 나옵니다. 어느 쪽이 더 좋은지 감만으로는 판단이 어렵습니다.

**감으로 판단하면 안 되는 이유**

- 사람마다 판단 기준이 다릅니다
- 질문 몇 개로는 전체를 대표할 수 없습니다
- 개선 방향 결정이 불가능합니다 ("뭘 더 개선해야 하지?"에 답할 수 없음)

이런 한계를 극복하기 위해 평가 체계가 필요했습니다.

## 2. RAG 평가의 핵심 지표

RAG 평가는 두 단계로 나누어 진행합니다.

### 검색(Retrieval) 평가

| 지표 | 측정 대상 |
|---|---|
| Context Precision | 검색된 청크 중 진짜 관련 있는 비율 |
| Context Recall | 정답을 빠짐없이 검색했는지 |

### 생성(Generation) 평가

| 지표 | 측정 대상 |
|---|---|
| Faithfulness | 답변이 컨텍스트에 충실한가 (환각 여부) |
| Answer Relevancy | 답변이 질문에 직접적으로 답하는가 |

이 4가지가 RAGAS의 핵심 지표입니다. 모든 지표가 0~1 사이 값이며 1에 가까울수록 좋습니다.

### RAGAS의 작동 원리 — LLM-as-a-Judge

RAGAS는 **LLM 자체를 평가자로 사용**합니다. 예를 들어 Faithfulness 측정 과정은 다음과 같습니다.

```
1. LLM이 답변을 주장 단위로 쪼갬
   - "푸들 사료는 연령에 맞춰야 한다"
   - "매일 2회 급여한다"  
   - "노령견은 글루코사민이 좋다"

2. 각 주장이 컨텍스트에서 추론 가능한지 LLM에게 판단 요청
   - 주장 1: 컨텍스트에 있음 (1)
   - 주장 2: 컨텍스트에 없음 (0) → 환각
   - 주장 3: 컨텍스트에 있음 (1)

3. Faithfulness = 2/3 = 0.67
```

LLM이 채점한다는 점이 RAG 평가의 핵심이자 함정입니다.

## 4. 골든셋 작성

평가의 출발점은 **골든셋(질문 + 정답 답변의 쌍)**입니다.

골든셋은 다음 4가지 조건을 만족해야 합니다.

1. **다양성** — 한 종류 질문만 있으면 안 됨
2. **충분한 양** — 50개 이상 권장 (학습 목적은 20개로 시작)
3. **명확한 정답** — 데이터에 실제로 있는 정보로만
4. **사용자스러운 표현** — 격식 차린 문장보다 실제 사용자가 던질 법한 표현

### 골든셋 형식

```json
{
    "question": "다이아몬드 곡괭이로 캘 수 있는 광물은?",
    "ground_truth": "다이아몬드 곡괭이는 흑요석, 에메랄드, 다이아몬드, 네더라이트 잔해 등을 캘 수 있습니다.",
    "category": "items"
}
```

### 마크 RAG 골든셋 (20개)

마크 RAG의 데이터 분포:
```
일반정보:    3,698개
정밀조합법:    797개
커뮤니티팁:  5,728개
```

이 분포에 맞춰 5개 카테고리로 20개를 작성했습니다.

```
[A] 일반정보 (6개)    예: "워든은 어디서 나타나?"
[B] 정밀조합법 (4개)  예: "철 곡괭이 만드는 재료는?"
[C] 커뮤니티팁 (4개)  예: "초보자가 처음에 뭐 해야 해?"
[D] 의미 검색 (3개)   예: "야간에 안전하게 지내는 법"
[E] 비교/추천 (3개)   예: "철 곡괭이 vs 다이아몬드 곡괭이 차이"
```

### 골든셋 작성 시 유의점

골든셋 작성에서 가장 큰 함정은 **데이터에 없는 정보를 정답으로 쓰는 것**입니다. 평가를 돌렸을 때 정답이 없어서 RAG가 답을 못하는 경우, 그것이 RAG의 실패인지 데이터의 한계인지 구분이 어려워집니다.

작성 후 검증 절차를 거쳤습니다.

```bash
# 각 정답이 데이터에 정말 있는지 키워드 검색으로 확인
python search_chunks.py 워든
python search_chunks.py 비콘
python search_chunks.py 다이아몬드
```

검색 결과가 없으면 그 질문은 제거하거나 다른 질문으로 교체했습니다.

## 5. RAG 결과 수집

평가하기 전에 골든셋의 모든 질문을 RAG에 돌려서 답변과 검색 결과를 수집해야 합니다.

```python
# run_rag.py 핵심 흐름

for item in golden:
    question = item["question"]
    
    # 1. Hybrid Search 실행
    docs = hybrid_search(query=question, ...)
    contexts = [doc.page_content for doc in docs]
    
    # 2. LLM 답변 생성
    answer = chain.invoke({
        "context": "\n\n".join(contexts),
        "question": question,
    }).content
    
    # 3. 결과 저장
    results.append({
        "question": question,
        "ground_truth": item["ground_truth"],
        "answer": answer,
        "contexts": contexts,
    })
```

이 결과 파일(`rag_results.json`)이 다음 단계 RAGAS 평가의 입력이 됩니다.

## 6. 첫 번째 시행착오 — Gemini의 한계

처음에는 마크 RAG에서 이미 사용 중인 Gemini 2.5 Flash를 평가 LLM으로 사용했습니다. API 키도 이미 있고, 무료 티어가 있어서 비용 부담도 없었기 때문입니다.

결과는 처참했습니다.

```
[평가 결과]
answer_relevancy: 0.6413 (유효: 1/20)
context_recall: 0.0000 (유효: 1/20)
```

**20개 중 19개가 평가 실패.** Faithfulness와 Context Precision은 결과 dict에 아예 들어오지도 못했습니다.

### 디버깅

원인 파악을 위해 1개 샘플만으로 디버깅 스크립트를 작성했습니다.

```python
# debug_one.py — raise_exceptions=True로 진짜 에러 메시지 보기

result = evaluate(
    dataset=dataset,
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
    llm=ragas_llm,
    embeddings=ragas_emb,
    raise_exceptions=True,
)
```

핵심 에러가 드러났습니다.

```
File ".../ragas/metrics/base.py", line 481
    score = await asyncio.wait_for(timeout=180)
        TimeoutError
```

**3분 동안 0% 진행**. Gemini가 비동기 호출에서 응답을 못 보내고 있었습니다. 정확한 원인은 두 가지로 추정됩니다.

1. Gemini API의 비동기 호출에서 재시도가 끝없이 돌아 timeout 발생
2. Gemini가 한국어 + JSON 형식 출력에서 안정성 떨어짐

### OpenAI로 전환

OpenAI gpt-4o-mini로 전환했더니 평가가 정상 작동했습니다. 변경은 LLM 인스턴스 부분 한 줄이면 충분했습니다.

```python
# 변경 전
from langchain_google_genai import ChatGoogleGenerativeAI
llm = ChatGoogleGenerativeAI(model="gemini-2.5-flash", temperature=0)

# 변경 후
from langchain_openai import ChatOpenAI
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
```

비용도 매우 저렴합니다. 20개 평가에 약 **$0.05~0.10** 정도였습니다.

### 학습 포인트

> RAGAS는 OpenAI 기반으로 개발되어 호환성이 가장 좋습니다.  
> Gemini는 비용은 매력적이지만 비동기 + 한국어 환경에서 불안정합니다.  
> 평가 도구는 안정성이 핵심이므로, 비용을 약간 들여도 신뢰성 있는 LLM을 사용하는 것이 맞습니다.

## 7. 마크 RAG 평가 결과

OpenAI로 전환한 후 평가가 빠르게 (2~3분) 완료되었습니다.

```
faithfulness:      0.8561  (환각 거의 없음, 좋음)
answer_relevancy:  0.5267  (답변이 질문에 직접 안 답함, 낮음)
context_precision: 0.6122  (검색 정확도 보통)
context_recall:    0.5500  (정답 검색 절반만 성공, 낮음)
```

### 한 줄 요약

환각은 거의 없지만, 검색에서 정답 청크를 못 가져오는 경우가 많고 답변도 질문에 직접 답하지 않는 경향이 있습니다.

### 질문별 약점 패턴

질문별 점수를 분석해서 3가지 약점 패턴을 발견했습니다.

**패턴 A — 검색 자체가 실패한 경우**

```
질문 8 (비콘 재료):        모든 점수 0
질문 16 (엔드 차원 가는법): 모든 점수 0
```

답변에 "컨텍스트에 정보 없음"으로 나온 항목입니다. 데이터 자체에 해당 정보가 부족하거나 다른 키워드로 인덱싱되어 검색이 안 됨.

→ 개선 방향: 데이터 보강 또는 골든셋에서 제외

**패턴 B — 검색이 다른 페이지를 가져온 경우**

```
질문 1 (다이아몬드 곡괭이 광물): faith 0.25, recall 0
  → 답변에 "금 광석"이 들어감 (잘못 매칭)

질문 2 (워든 위치): recall 0, precision 0
  → 정답은 "고대 도시"인데 워든 행동 양식만 검색됨
```

→ 개선 방향: Re-ranking 도입 (현재 마크 RAG에는 미적용)

**패턴 C — 답변이 부분적**

answer_relevancy가 낮은 가장 큰 원인. 검색은 잘 됐는데 LLM이 컨텍스트의 일부만 활용.

→ 개선 방향: 프롬프트 강화

### 카테고리별 분석

```
일반정보 (6개):    faith 0.79, relevancy 0.53, precision 0.58, recall 0.50
정밀조합법 (4개):  faith 0.81, relevancy 0.41, precision 0.47, recall 0.25
커뮤니티팁 (4개):  faith 0.97, relevancy 0.61, precision 0.85, recall 0.75
의미 검색 (3개):   faith 0.97, relevancy 0.40, precision 0.50, recall 0.33
비교 (3개):        faith 0.93, relevancy 0.59, precision 0.88, recall 1.00
```

비교 질문이 가장 잘 작동하고, 정밀조합법(비콘, 마법 부여대 등)이 가장 약합니다. 이는 비교 질문이 두 청크를 가져와 답하는 RAG 패턴에 적합한 반면, 정밀조합법은 정확한 페이지를 찾아야 하는 정밀 검색이 필요하기 때문입니다.

## 8. 두 번째 시행착오 — 평가는 운영 환경과 동일해야 한다

YT RAG에 같은 평가를 적용하면서 또 다른 문제를 발견했습니다.

### 평가 결과

```
faithfulness:      0.40  (마크 RAG는 0.86)
answer_relevancy:  0.53
context_precision: 0.60
context_recall:    0.60
```

**Faithfulness가 절반 이하로 떨어졌습니다.** 답변에 환각이 많다는 신호인데, 답변 내용을 보면 그게 아니었습니다.

### 답변 내용 확인

```
Q: "풍향고가 뭐야?"
A (실제 답변): "풍향고는 유재석, 황정민, 지석진, 양세찬이 출연하는 
                여행 예능 프로그램으로, 'NO어플, NO예약' 즉흥 여행을 
                주제로 합니다..."

Q: "유재석이 진행하는 채널은?"
A: "유재석이 진행하는 채널은 채널십오야입니다."
   → 정답은 "뜬뜬" (유재석의 핑계고 채널)
```

답변이 완전 잘못된 게 아니라, **질문 자체가 모호하거나 검색이 회차 위주로 작동**하면서 발생한 문제였습니다.

### 진짜 원인

YT RAG의 실제 운영 코드를 다시 보니, `llm.py`의 `generate_episode_answer` 함수가 매우 정교한 프롬프트를 사용하고 있었습니다.

```python
# 운영의 실제 프롬프트 (요약)
"""
너는 유튜브 채널 영상을 찾아주는 도우미야.
- 영상 제목 (가장 신뢰도 높음)
- 영상 설명(description) — 출연자/회차/줄거리 핵심 정보
- 자막 발췌 — 실제 대사. 사람 이름은 잘못 들리거나 다르게 적힐 수 있음
- 관련도 점수 — 0~1.2 사이, 높을수록 의미상 가까움

원칙:
- 한국어, 친근하고 간결하게
- 출연자 이름은 자막의 음차 표기보다 영상 설명·태그를 우선시해
- 후보가 N개면 점수가 가장 높은 1번이 정답일 가능성이 가장 높음
..."""
```

반면 평가용 `run_rag.py`에 작성했던 프롬프트는 다음과 같이 단순했습니다.

```python
"""당신은 한국어 유튜브 채널 콘텐츠 분석 전문가입니다.
컨텍스트에 없는 내용은 답하지 마세요. 모르면 모른다고 답하세요."""
```

**평가에서 사용한 프롬프트가 실제 운영 프롬프트와 달랐던 것**이 점수가 낮게 나온 주된 원인이었습니다.

### 학습 포인트

> 평가는 실제 운영 환경과 동일한 조건에서 진행해야 의미가 있습니다.  
> 평가용으로 별도 프롬프트를 작성하면, 운영의 진짜 성능을 측정하는 것이 아니라  
> "평가용으로 작성한 코드"의 성능을 측정하게 됩니다.

이 문제는 운영의 `generate_episode_answer`를 그대로 import해서 사용하는 방식으로 해결했습니다.

## 9. 추가로 발견한 인사이트

### 1. 골든셋 자체가 평가의 한계

YT RAG 골든셋에 "유재석이 진행하는 채널은?"이라는 질문을 넣었는데, 평가에서 매우 낮은 점수가 나왔습니다. 답변 분석 결과, **유재석이 모든 채널에 언급되어 있어 정답이 단일하지 않은 모호한 질문**이었습니다.

> 골든셋의 질문은 정답이 명확하게 하나여야 합니다.  
> "재밌는 회차" 같은 주관적 질문이나, "유재석이 진행하는 채널" 같은  
> 정답이 여러 개일 수 있는 질문은 골든셋에서 제외해야 합니다.

### 2. LLM-as-a-Judge의 노이즈

같은 답변에 대해서도 평가 LLM이 매번 약간씩 다른 점수를 매기는 경우가 있습니다. 예를 들어 컨텍스트에 정답이 명확히 있는데도 faithfulness가 0.5로 나오는 경우 등.

→ 5개 같은 적은 표본으로는 통계적 신뢰성이 떨어집니다. 최소 20개, 가능하면 50개 이상의 골든셋을 권장합니다.

### 3. 운영 환경의 답변 형식과 골든셋 형식의 불일치

YT RAG의 운영 답변은 "찾으시는 영상은 X입니다" 형식인데, 골든셋의 정답은 "EP.78 게스트는 박보검, 이상이, 김소현입니다" 같은 정보 추출 형식입니다.

같은 정보를 담고 있어도 형식이 다르면 answer_relevancy가 낮게 측정될 수 있습니다.

→ 골든셋을 운영 답변 형식에 맞추거나, 운영 답변을 다양한 질문 유형에 맞게 분기 처리해야 합니다.

## 10. 베이스라인 확립과 다음 단계

이번 평가로 두 RAG의 **베이스라인**을 확립했습니다.

| 지표 | 마크 RAG | YT RAG (5개) |
|---|---|---|
| Faithfulness | 0.86 | 0.40 |
| Answer Relevancy | 0.53 | 0.53 |
| Context Precision | 0.61 | 0.60 |
| Context Recall | 0.55 | 0.60 |

이 베이스라인은 **개선이 진짜 개선인지 판단하는 기준**이 됩니다. 앞으로 어떤 개선 작업을 하든 이 점수와 비교하면 됩니다.

### 우선순위 정리된 개선 방향

1. **Re-ranking 도입** (Day 5에서 배운 내용)
   - 패턴 B (검색이 다른 페이지를 가져오는 경우) 해결 예상
   - Context Precision, Recall 개선 효과 클 것

2. **프롬프트 개선**
   - 패턴 C (답변이 부분적) 해결
   - Answer Relevancy 개선

3. **YT RAG의 Intent 분기 추가**
   - "풍향고가 뭐야?" 같은 개념 질문을 영상 찾기와 다르게 처리
   - 콘텐츠/인물 설명 전용 답변 흐름 추가

4. **데이터 보강** (마크 RAG의 패턴 A 해결)
   - 비콘, 엔드 차원 등 누락된 페이지 추가 크롤링

## 11. 마무리 — 평가가 주는 것

평가 체계를 갖추는 작업은 화려하지 않습니다. 새 기능을 추가하는 것이 아니라 기존 시스템을 측정하는 도구를 만드는 작업입니다. 하지만 평가 없이는:

- 개선이 진짜 개선인지 알 수 없습니다
- 어디를 먼저 개선해야 할지 결정할 수 없습니다
- 사용자에게 "우리 시스템의 정답률은 X%입니다"라고 말할 수 없습니다

이번 작업에서 가장 큰 교훈은 두 가지였습니다.

> **첫째, 도구의 선택이 평가 결과를 좌우합니다.**  
> Gemini와 OpenAI는 비용 차이만 있는 게 아니라 안정성 자체가 달랐습니다.
> 
> **둘째, 평가는 운영 환경의 거울이어야 합니다.**  
> 평가용 별도 프롬프트를 쓰면 그 프롬프트의 성능을 측정하는 것일 뿐,  
> 실제 운영 시스템의 성능이 아닙니다.

다음 작업은 이 베이스라인 위에서 Re-ranking을 도입하고, 그 효과를 수치로 검증하는 것입니다. 평가 체계의 진짜 가치는 그 시점에 드러납니다.
