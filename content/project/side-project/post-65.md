**2026년 5월 중순**을 데드라인으로 두는 **가제 ‘SOUND of VOICE’** 보스전 데모를 위해, **MCP**와 **AI 에이전트**(Cursor 등)를 어떻게 쓸지 전체 과정을 **4개 페이즈**로 나누고 **작업 주체**와 **프롬프트 전략**을 구조화해 둔 메모임. 두 번째 사이드 프로젝트(게임·MCP 축)의 설계 문서 역할을 함.

---

### Phase 1: 기획 및 데이터 구조화 (사용자 주도)

이 단계에서는 AI가 나중에 **코드로 옮기기 쉽도록** 기획을 **데이터**와 **논리 구조**로 번역하는 데 집중함.

**User (기획·명세)**

*   **판정 로직 수치화:** Perfect / Good / Miss에 대한 **시간 오차 범위(ms)** 를 표로 고정. 감으로 두면 AI도 엔진도 같은 기준을 못 씀.
*   **보스 패턴 데이터화:** 2~3개 패턴을 **타임라인 기반** 구조(JSON, CSV 등)로 설계. 특정 시각에 어떤 노트 종류·위치·속도가 나오는지 **명시적 필드**로 적어 둠.
*   **입출력 정의:** 오디오·입력·렌더링 사이 **데이터 흐름**을 간단한 구조도로 그림. “누가 누구에게 무엇을 넘기는지”가 없으면 모듈 경계가 흐트러짐.

**AI / MCP**

*   이 단계에서는 **본격 코드 생성은 하지 않음.** 사용자가 쓴 JSON·스키마에 대해 **유효성 검증**, **타입/인터페이스 초안** 정도만 AI에 맡겨 형태를 맞춤.

---

### Phase 2: 환경 구축 및 아키텍처 설계 (협업)

Cursor와 MCP를 붙이고, 프로젝트 **뼈대**를 잡는 단계임.

**User (환경 통제)**

*   Cursor 설정, 로컬 파일·터미널을 다룰 수 있는 **MCP 서버** 연동.
*   **코딩 컨벤션**, 디렉터리 규칙, 상태 관리 방식(MVC/MVP 등)을 문서로 고정하고 **Rules / 시스템 프롬프트**에 반영해 에이전트가 같은 규칙을 보도록 함.

**AI / MCP (스캐폴딩)**

*   위 지침에 맞춰 **폴더 구조** 생성.
*   **GameManager**, **AudioController**, **RhythmEngine**, **BossController** 같은 핵심 클래스의 **스켈레톤·인터페이스**를 먼저 깔고, 구현은 다음 페이즈로 미룸.

---

### Phase 3: 핵심 시스템 모듈별 구현 (AI 주도)

아키텍처 위에서 **실제 동작 로직**을 모듈 단위로 쌓음. 결합도를 낮추기 위해 **한 모듈씩** 격리해서 진행.

**User (오케스트레이션·검증)**

*   모듈별 **구체 프롬프트** 작성·입력.
*   생성 코드를 빌드하고 **기대 로그·동작**과 대조. 버그 시 원인 추론을 AI에게 맡기기보다 **현상 + 에러 로그**만 넘겨 수정을 요청하는 편이 반복이 빠름.

**AI / MCP (코드 생성)**

1.  **리듬 엔진:** 재생 시각과 입력 시각 비교 **판정**, 필요 시 **오디오 레이턴시 보정**.
2.  **패턴 파서:** Phase 1 데이터를 읽어 메모리에 올리고, 시간에 맞춰 **이벤트 방출(Emit)**.
3.  **렌더링 연동:** 이벤트에 맞춰 **임시 도형/UI** 스폰, 판정 결과에 따른 피드백.

---

### Phase 4: 통합 및 폴리싱 (협업)

모듈을 하나의 **데모 빌드**로 묶고 마감하는 단계임.

**User (에셋·밸런스)**

*   임시 **도트·사운드**를 프로젝트 경로에 배치.
*   판정 난이도·보스 패턴 **템포**는 데이터 파일만 수정해 조정 (코드보다 데이터로 튜닝).

**AI / MCP (최적화·디버깅)**

*   지정한 **에셋 경로**를 코드에 매핑.
*   통합 과정에서 **메모리 누수**, **싱크 어긋남** 등을 프로파일링하고 병목 위주로 최적화.

---

### AI 에이전트 통제용 프롬프트 엔지니어링

환각을 줄이고 **의도한 파일·의도한 API**만 건드리게 하기 위한 규칙임.

1.  **인터페이스 우선 (Interface-First)**  
    “보스 패턴 로직 짜줘”보다 **“`BossController`의 입출력 시그니처와 필수 속성만 먼저 정의해 줘”**처럼 **계약**을 먼저 고정한 뒤 구현을 요청함.

2.  **컨텍스트 스코프 제한 (Context Bounding)**  
    프로젝트 전체를 풀로 열어 두면 엉뚱한 파일이 수정될 수 있음. Cursor의 **`@파일명`** 으로 **수정 대상**과 **참조할 인터페이스/데이터**만 좁혀서 지시함. (예: “`RhythmEngine` 구현 중이며, 판정 기준은 `TimingData.json`을 따른다.”)

3.  **단계별 검증 (Chain of Implementation)**  
    한 번에 끝내지 않고, **파싱 → 로그 확인 → 타이머 → 스폰**처럼 쪼개서 매 단계 **실행 결과**를 본 뒤 다음 프롬프트로 넘어감.

4.  **부작용 방지 (Zero-Side-Effect Constraint)**  
    프롬프트 하단에 상시: **지시 범위 밖의 기존 메서드·필드는 건드리지 말 것**, 새 동작은 **독립 함수**로 추가할 것 — 등을 붙여 회귀를 줄임.

---

### 마무리

이 글은 **완성된 데모 설명**이 아니라, 5월 중순까지 **돌아가는 보스전 데모**를 만들기 위한 **협업 규약** 정리임. 이후 브랜치에서는 실제로 **어떤 엔진/언어 조합으로 스켈레톤을 깔았는지**, **패턴 JSON 스키마 v1**이 어떻게 생겼는지처럼 구체 로그를 이어서 남길 예정임.
