### 1. Intro: 왜 게임 개발을 굳이 따로 연구해야 하나

게임은 이미 일반 리테일 소프트웨어보다 **3배 큰 매출**(2012년 기준)을 내는 거대 산업임. 그런데도 SE 학계가 분석한 116개 OSS/CSS 프로젝트 중 게임은 단 **3개**뿐. SIR/Qualitus 같은 SE 연구 코퍼스에서도 게임 비중은 0~3%에 그침.

이게 왜 문제냐. 만약 **게임 개발이 일반 SW 개발과 실제로 다르다면**, 지금까지의 SE 연구·도구·교과서는 게임 개발자에게 거의 쓸모가 없다는 뜻임. 의학계가 한때 관상동맥 질환 연구를 남성 위주로 진행해서 여성용 치료법이 부실해진 사례를, SE가 게임에서 그대로 반복하고 있을 수 있음.

이 논문은 이 질문에 **최초로 광범위한 실증 데이터로 답한 연구**임. "다르다 vs 같다"의 이분법이 아니라, **어디가 어떻게 다른가**를 체계적으로 본다.

### 2. Methodology: Interview + Survey의 Mixed-Method

저자들은 두 가지 데이터를 결합함.

#### [A] Interview (14명)

LinkedIn의 "Game Development" 그룹(당시 65,000명) 중, **게임/비게임 양쪽 모두 2년 이상 경험**이 있고 특정 타이틀에 기여한 이력이 있는 207명을 필터링. 그중 38명을 컨택해 **14명**(P1~P14)을 인터뷰. 새로운 차이점이 더 안 나오는 *saturation* 지점에서 멈춤.

인터뷰는 4단계 구조임.

1. 데모그래픽 질문
2. Open-ended: "게임 vs 비게임 개발의 차이가 뭐라고 생각함?" (인터뷰어 편향 최소화)
3. 인터뷰이가 직접 **SWEBOK 10개 영역** 또는 **Humphrey 등의 General Work Topics**에서 2~3개를 골라 토의
4. 인터뷰어가 **가장 적게 다뤄진 토픽**을 선택해 추가 질문 → 토픽별 최소 2회 커버

#### [B] Survey (Microsoft 내부, 응답률 40%)

인터뷰 결과로 84개 후보 문항을 도출 → **28개 최종 문항**, 5점 Likert 척도로 압축. 세 그룹에 각 300명씩 발송:

* **Games**: MS 게임 부서 (engineer 113 + tester 32)
* **Office**: MS Office 부서 (engineer 61 + tester 39) — 동일 회사 내 *homogeneous* 비교군
* **Other**: MS 전사에서 위 둘이 아닌 사람 (engineer 82 + tester 37) — *diverse* 비교군

> **[사진추가]** — 인터뷰/설문 demographics 표 (논문 p.3, p.4의 작은 표 두 개). 표본 규모 감 잡는 용도.

분석은 Wilcoxon rank-sum test, Benjamini-Hochberg 보정 후 α=.016 기준. 결과는 4가지로 라벨링됨 — Games vs (Office *and* Other) 둘 다 유의차 / 둘 중 하나만 유의차 / 무유의차 / 반대 방향.

### 3. SWEBOK Topics에서 발견된 차이

#### 3.1 Software Requirements — 단 하나의 요구사항: "Fun"

거의 모든 인터뷰이가 동의함. 게임의 요구사항은 본질적으로 단 하나, **"재미있어야 함"** [S6 유의차].

> "디자이너가 어떤 feature를 원한다고 high-level goal을 줘. 근데 자기도 자기가 뭘 원하는지 잘 모름." (P3)

비게임 SW는 명확한 functional requirement가 있지만, 게임은:

* **재미는 만들어보기 전엔 모름** — 비전대로 구현했는데 안 재밌으면 폐기
* **사용자 timescale이 다름** — 이커머스는 몇 분짜리 task, 게임은 수개월 동안 매일 수 시간
* **failure cost가 다름** — 이메일 전송 실패는 해고 사유지만, 게임 1회 미흡은 유저가 그냥 떠나면 끝 (P1)

#### 3.2 Software Design — 설계는 사치

"fun" 요구사항이 흐릿하니 사전 설계도 흐릿함 [S5, S8]. 코드 폐기 가능성이 높은 상태에서 미리 설계해두면 그게 다 낭비가 됨.

> "디렉터가 1~2주 뒤에 마음을 바꿀 걸 알기 때문에, 미리 설계를 자세히 하려고 하지 않음." (P11)

흥미로운 패러독스 — 게임은 일찍부터 **architectural debt**가 쌓임 [S3, S4]. 어차피 폐기될 거니 그게 합리적이지만, **그 게임이 성공해버리면** 그 빚을 결국 갚아야 함.

#### 3.3 Construction, Tools, Methods — Tool Pipeline이 게임 본체만큼 큼

게임은 **코드 재사용이 적음** [S1]. 성능 튜닝이 게임마다 특수하고, "게이머는 항상 새로운 경험을 원함"이라 차별화 자체가 산업 본질이라 그렇다.

> "[같은 회사에서] 게임 [X]개에 오디오 프로그래머로 들어가서 [X]개의 다른 오디오 엔진을 짰음." (P11)

대신 게임에는 **In-house Tool Pipeline**이 어마어마함 [S15]:

> "Maya/Max에서 3D asset을 추출해 우리 엔진이 로드할 수 있는 native format으로 변환하는 도구를 직접 만듦. tool pipeline이 게임 자체보다 클 때도 있음." (P5)

#### 3.4 Software Testing & Quality — Cowboy Coder 등장

게임에서 가장 극적인 차이. **Automated test가 거의 없음.** 사람이 직접 플레이하거나 [S16], 사람 흉내 스크립트로 [×S17] 테스트함.

이유는 4가지:

1. **UI 분리가 어려움** — MVC 같은 패턴이 안 통함. 사용자 인터랙션이 게임의 본질이라 떼어낼 수가 없음.
2. **State space 폭발** [S19] — 유저가 만들 수 있는 상태가 너무 많음.
3. **무엇이 옳은지 정의가 어려움** — "적이 2발에 죽는다"가 아니라 "디자이너가 좋다고 생각하는 발수"여야 함. (P12)
4. **Non-determinism** — Multithreading + AI + 멀티플레이 + 의도적 randomness가 한꺼번에 섞임.

그리고 결정적인 한 줄:

> "디자이너가 너무 자주 마음을 바꿔서, 자잘한 [test] 수정이 사방에서 일어남." (P12)

즉 **자동화 테스트는 디자인 변경에 약하고**, 사람 테스트가 강함. 게다가 게임 플레이 테스터는 SW 테스터보다 훨씬 쌈.

여기서 **Cowboy Coder**가 등장함. 변경이 잦고 자동화는 약하니, 그 위기를 손으로 막아내는 "영웅적 개인"이 필수가 됨. 좋은 의미만은 아님 — 매니지먼트는 그 덕에 진짜 문제를 못 봄 (P3).

#### 3.5 Software Maintenance — "내가 마지막일 거야"

유지보수도 의도적으로 미뤄짐.

> "게임에는 '내가 이 코드를 만지는 마지막 사람일 거야'라는 정서가 있음." (P12)

이유는 design처럼 — 성공 못 하면 폐기되니 미리 유지보수성에 투자하는 게 낭비라는 계산. 게다가 매니지먼트가 비기술자라 [S21] 클린코드의 가치를 설득하기도 힘듦.

다만 **Steam 같은 cloud-based 서비스의 등장**으로 게임 유지보수가 일반 SW에 가까워지고 있다는 점을 짚음 — 2014년 시점의 관찰이라는 걸 감안해 읽어야 함.

#### 3.6 Configuration Management — Asset이 시한폭탄

자동화 테스트가 없으니 **자동 빌드 = smoke test**가 됨. 그만큼 더 중요해지지만 동시에 chaotic.

* **Code review 부족** [S2]
* **Asset / Resource** 자체가 형상관리 부담 — 코드와 달리 asset은 빌드 시점에 부서지면 곧장 크래시
* **Artist의 형상관리 미숙** — 코드는 모듈 단위로 격리되지만, asset은 한 명의 실수가 전체 빌드를 망가뜨림 (P11)

#### 3.7 Engineering Management — 비기술자가 위에 있음

> "내가 두 큰 게임 회사에 있는 동안 보고했던 매니저들의 절반은 엔지니어링 경험이 아예 없었음." (P3)

비기술자 매니저가 만들어내는 결과:

* **엔지니어링 이슈 소통이 어려움** [S22] — 한 사람이 어려운 frame rate 버그 1개로 막혀 있는 동안 다른 사람이 UI 오탈자 30개를 고쳤다는 게 왜 정상인지를 설명해야 함
* **즉시 매출에 안 보이는 활동(refactoring 등)은 무시당함**
* SE 실천 도입은 **bottom-up** [S23] — 매니저가 아니라 엔지니어가 주도

#### 3.8 Engineering Process — Agile, 또는 Hacking

인터뷰이 14명 중 9명이 "Agile"이라는 단어를 직접 씀 [S9 유의차]. 다만 그게 진짜 Agile인지는 별개 [S10]:

> "Agile 모드, 아니면 hacking 모드... 거의 완전한 hacking인데, 정말 똑똑한 사람들이 많아서 굴러감." (P2)

그리고 deadline이 살벌함 [S14]:

> "크리스마스를 옮길 수는 없잖아." (P4)

### 4. General Work Topics

#### 4.1 Problem Solving — 게임은 진짜 어려움 [S25]

* **고급 수학과 그래픽 특화 지식** 필요
* **메모리 fragmentation, disk load time** 같은 시스템 수준 최적화
* **재미는 주관적** — 문제 정의 자체가 어려움
* **요구되는 스킬셋이 넓음** [S12] — 비즈니스 SW는 좁고 깊은 반면, 게임은 그래픽 / 물리 / AI / 오디오 / UI / 플랫폼 모두 필요

#### 4.2 Specialization — Keepers of Quality

> "디자이너와 아티스트가 quality의 keepers임. 개발자보다 그들이 어색한 걸 더 잘 느낌." (P6)

이 표현이 논문 제목의 세 번째 단어임. 그리고 게임 팀에는 일반 SW에서 잘 안 보이는 specialist가 들어옴 — **사회학자, 인류학자, 경제학자**까지. 디아블로 3의 가상 화폐 인플레이션 사건 이후로 game economist를 두는 회사가 늘었다는 일화가 등장함 (P2).

#### 4.3 Knowledge of Results — Celebrity Status

유저 참여도가 일반 SW와 비교가 안 됨 [S26]:

> 외국 택시기사에게 "특정 레이싱 게임 시리즈 개발자"라고 말했더니, 친구들에게 전화를 돌리며 자랑하더라. (P7)

흥미로운 양면 — 인터뷰이 P2는 5년간 개발한 FPS를 **한 번도 끝까지 플레이해본 적 없다**고 함 [S27]. "영화 배우가 자기 영화 보기 싫어하는 것과 같음."

#### 4.4 Significance — "그래도 그냥 게임인데요"

의외의 발견 [S28]: 게임 개발자들 스스로 **자신의 작업이 비게임 SW보다 사회적 의미가 적다고 느낌**.

> "우리도 알아요, 그냥 게임 만드는 거고, 비즈니스 크리티컬한 소프트웨어만큼 중요하진 않다는 걸." (P8)

그래도 의미를 찾는 부분은 있음 — 가족 단위 사교, 감정적 영향력, "긍정적 기억". P2는 자신의 일을 "마약 파는 것"에 비유하며 양가감정을 드러내기도 함.

#### 4.5 Physical Demands — Ankle Sprains

이 섹션이 논문 제목의 두 번째 단어를 만들어냄.

* **Crunch time** — 12개월 동안 주말마다 가족을 못 보는 게 흔함. 2004년 EA Spouse 공개서한 일화도 등장
* **Wii / Kinect 테스터들의 발목 염좌** — 점프하고 숙이고 하다가 진짜로 발목을 삠 (P6)
* **FPS 개발자들 = 수년간 가상 총소리에 노출**
* **High-energy 환경** — 음악, 잡담, 복도에서 풋볼 던지기. 일부 개발자는 너무 시끄러워서 집에서 일함
* **Motion Sickness** — 개발 중 low frame rate / 미튜닝 환경을 오래 봐서 멀미가 생긴다는 주장. 저자들이 진짜로 MS 직원 165명 대상 모션 멀미 설문까지 했지만, **유의차는 없었음** (별도 technical report로 발표 [38]). 진지함과 유머가 공존하는 부분.

### 5. Survey 결과 — 통계적으로 유의한 차이는?

설문은 인터뷰의 일부 주장을 **무효화**하고, 일부를 **확정**시킴.

> **[사진추가]** — Table 1. Survey Results 전체. 28개 항목의 Likert distribution + Effect Size + p-value가 들어있는 큰 표 (논문 p.9).

Benjamini-Hochberg 보정 후 α=.016 기준에서, **Games 그룹이 Office *and* Other 양쪽 모두와 통계적으로 다르게 답한 항목**, 즉 "확실히 게임 개발이 다르다고 말할 수 있는 항목"은 다음 6개임.

* **S6** — 요구사항이 덜 명확함
* **S9** — Agile 프로세스 인식이 더 강함 (waterfall에 동의 안 함)
* **S11** — 창의성이 더 중시됨
* **S12** — 다양한 스킬셋의 팀이 필요함
* **S13** — 비엔지니어와의 소통 능력이 더 가치 있음 (effect size 1.2~1.3으로 압도적)
* **S26** — 회사 밖 사람들이 "내가 만드는 SW"를 듣고 더 감명받음

반면 인터뷰에서 강하게 나왔지만 설문에서는 무너진 항목도 있음 — 예: **엔지니어를 매니지먼트로 보내는 문화 [S24]**는 세 그룹 차이가 거의 없었음. 저자들은 "Microsoft 전사 문화에 묻혀버린 케이스"로 해석함. **정성 결과만 믿으면 안 된다는 것을 본인들 결과로 증명한 셈**.

### 6. Limitations — 저자들이 직접 짚는 한계

1. **표본 한계** — 인터뷰 14명, 설문은 Microsoft 내부만. 다만 MS 게임팀이 MS 비게임 문화에 오염됐을 가능성이 있음에도 차이가 검출된 건 오히려 강한 신호임
2. **LinkedIn 편향** — LinkedIn에 프로필을 두는 사람들의 편향이 있을 수 있음
3. **차이 위주 질문 설계** — 인터뷰 구조 자체가 차이를 강조하게 유도했을 가능성
4. **주관성** — "Agile" 같은 용어를 사람마다 다르게 씀
5. **동질화 가정** — "게임 개발자"를 하나의 그룹으로 봤지만, 실제로는 팀마다 다름. 모바일/인터넷 게임은 또 다를 것

### 7. Implications

**Research.**
* Non-determinism 환경의 테스트 (CHESS [40] 같은 thread interleaving 도구의 확장)
* 거대 state space 탐색 기법
* "올바른 행동"을 **유연하게** assertion하는 기법
* **Content/Asset 변경에서 발생하는 버그**의 조기 탐지 — 기존 SE 연구는 source code만 봄
* **In-house tool** 자체의 SE 연구 — 어떤 기능을 자체 제작하나? 어떻게 진화하나? 누가 유지보수하나?

**Practice.**
* 매니지먼트를 격리시키지 말고 **엔지니어링 이슈를 공유**할 것 — SE 실천 도입의 핵심
* High-overhead SE 실천은 게임에 안 맞을 수 있지만, **pair programming / remote code review** 같은 low-overhead는 잘 맞음
* 일반 SW도 게임에서 배울 점 있음 — **사용자 이해에 대한 집착** 자체는 어느 도메인에서도 가치 있음

**Education.**
* 게임 분야로 갈 학생에게 첫 번째 기술은 **비엔지니어와의 소통**
* "엔지니어가 아닌 역할에서 일해보는 경험"이 도움됨
* 수학과 성능 튜닝의 강화

### 8. Engineer's Insight — 2014년의 논문이 2026년에 주는 것

이 논문은 **알고리즘이 아니라 직군 인류학에 가까운 글**임. 그래서 12년이 지난 지금 읽어도 신선한 부분이 많고, 의외로 LLM/생성형 AI 제품 개발과 닮은 점이 많음.

**1. "Fun" 요구사항의 본질은 LLM 시대에도 그대로임.**
LLM 제품을 만들다 보면 똑같은 문제를 만남 — "쓸 만한가 / 재밌는가 / 자연스러운가"는 functional requirement로 안 잡힘. PM이 "어… 그게 아닌데"를 반복함. 이 논문이 게임에서 발견한 **"creative requirement는 사전 명세가 안 되고 점진적으로 수렴한다"**는 통찰은 그대로 생성형 AI 제품에 옮겨 적용 가능함.

**2. 자동화 테스트의 약점은 LLM 평가에서 거의 그대로 반복됨.**
"적이 2발에 죽어야 한다"가 unit test로 안 잡힌다는 P12의 토로는, RAGAS 점수가 답변 품질을 못 잡는 문제와 형태가 같음. 디자이너의 의도가 자주 바뀌니 테스트가 obsolete해진다는 부분도 LLM 프롬프트 개발과 닮음. 사이드 프로젝트로 RAGAS를 굴려본 입장에서, 게임 개발자들의 "그냥 사람이 플레이하는 게 낫다"는 결론이 묘하게 공감됨.

**3. In-house Tool Pipeline이 본체보다 크다.**
"tool pipeline이 게임 자체보다 클 때도 있다"는 P5의 말은 12년이 지난 지금 더 사실에 가까움. AI 인프라 회사들이 자기네 학습/평가 파이프라인이 모델 코드보다 크다고 말하는 것과 정확히 같은 구조임.

**4. Cowboy Coder 비판은 여전히 유효함.**
"잘 막아내는 영웅"이 있으면 매니지먼트가 진짜 문제를 못 본다는 P3의 통찰은 어떤 조직에서든 한 번쯤 본 풍경임. 영웅 의존도는 결국 시스템의 약점을 가린다.

**5. Mixed-Method 자체의 가치.**
인터뷰에서 강하게 나온 주장 중 일부([S24] 등)가 설문에서 무너졌다는 건, **정성+정량의 결합이 실제로 작동한다는 증거**임. 인터뷰만 했으면 잘못된 결론을 자신 있게 발표했을 것. 사내 사용자 리서치나 제품 A/B 테스트를 설계할 때도 그대로 적용할 만한 교훈임.
